4  アルゴリズムの性質

4.1 本章のねらい

コンピュータに問題を解かせるための明確な手順である「アルゴリズム」の基本的性質を理解します。アルゴリズムが必ず有限時間で終了する「停止性」と、計算資源（時間・メモリ）の増大度合いを評価する「計算量（オーダー記法）」の概念を学びます。また、今後の講義で実践する coding agent（AIコーディング支援環境） の利用方法として、従来のchat型AIとの相違点、本講義で活用するツール環境（Antigravity等）の使い方や導入手順、そして weekly quota（週間利用枠）の消費を抑えて効率的にプログラミングを進めるための重要なテクニックを習得します。

本科目におけるプログラミングの方針（Vibe Coding）
本章以降では、学生の皆さんがプログラムのソースコードを一から手書きするのではなく、AI coding agent（Antigravity等）に対して「どのようなプログラムを作成するか」という明確な要件・指示（プロンプト）を与えて協調的に実装を進める vibe coding を行います。

4.2 coding agentの利用

近年、大規模言語モデル（LLM）の発展により、自然言語による仕様や要求をもとに自律的にコードを生成・修正・テスト・実行する coding agent（コーディングエージェント） が実用化されています。

4.2.1 chat型の生成AIとcoding agentの比較

これまでにChatGPTやClaude、GeminiなどのWebブラウザ上で対話する「chat型生成AI」を利用したことがある人も多いでしょう。coding agentはこれらとどのように異なるのでしょうか。

比較項目 chat型生成AI coding agent（Antigravity等）
主な用途 質問への回答、アイデア出し、スニペットの提示 プロジェクト全体の開発、ファイル生成・編集、テスト実行
作業環境へのアクセス 原則なし（画面上のテキスト対話のみ） 作業フォルダ内のファイル読込・書込、ターミナルコマンド実行
コードの適用方法 人間がコードをコピー＆ペーストして配置 エージェントが直接ファイルを新規作成・差分修正
エラーへの対応 人間がエラー画面をコピーして再質問 エージェント自身がテストを実行し、自律的にエラーを修正
適したタスク 概念の学習、一般的な質問、ブレインストーミング 実際のソフトウェア作成、デバッグ、環境構築

chat型AIが「相談相手の家庭教師」であるとすれば、coding agentは「机の隣で一緒にキーボードとマウスを操作してくれるペアプログラマー」と言えます。

4.2.2 Antigravityの使い方

本科目で活用する開発支援エージェント「Antigravity」は、ターミナル操作、ファイル作成・編集、テスト実行などを一貫して行える高機能なcoding agent環境です。

4.2.2.1 インストール方法

Antigravityは講義環境や各自の開発マシンにインストールして使用します。 1. インストーラの取得: 指定された配布サイトまたは公式ドキュメントより、使用しているOS（macOS / Windows / Linux）向けのインストーラをダウンロードします。 2. 実行・導入: 指示に従ってセットアップを行い、VS Code連携やコマンドラインツール（CLI）の設定を完了させます。 3. 起動と初期設定: ターミナルから agy コマンドを実行するか、VS Codeの拡張機能パネルからAntigravityを起動し、APIキー等の認証情報を設定します。

4.2.2.2 基本的な利用サイクル

  1. 仕様の明確化: 何を達成したいのか、入力・出力、環境の前提条件を自然言語で明確に定義します。
  2. エージェントへの指示（プロンプト）: 「どのようなプログラムを作成するか」を論理的・構造的に指示します。
  3. 提案コードの検証と実行: エージェントが生成したコードの内容を確認し、自動テストや動作確認コマンドを実行して期待通りの挙動を示すか検証します。
  4. 対話による反復改善: エラーや想定と異なる動作があれば、エラーログや所望の修正点をエージェントにフィードバックして修正させます。

4.2.3 weekly quotaの消費を抑えるにはどうすればよいか

多くの最新AIコーディングエージェントには、1週間あたりに利用できるリクエスト回数や計算資源の制限（weekly quota）が設けられています。制限に達すると週の更新日までエージェントが利用できなくなってしまいます。

限られた枠の中で最大限の成果を上げるための鉄則は、「検索やアイデア出しなど、coding agentでなくてもできる仕事は、他のAIを使う」ことです。

  1. 検索やアイデア出しには通常のchat型AIを活用する: 「Pythonで迷路を作るアイデアを出して」「Gymnasiumのライブラリの概要を教えて」といった一般的な質問や調査は、coding agentではなく無料または枠の大きなchat型AI（GeminiやChatGPTなど）を使って事前に行います。エージェントには「方針が固まった後の実装」のみを依頼します。
  2. 指示（プロンプト）を具体的に1回にまとめる: 「動かないので直して」のような曖昧で断片的な指示を何度も繰り返すと、quotaを無駄に浪費します。エラーメッセージ全体、実行したコマンド、期待する動作を最初のプロンプトにすべて含めて指示します。
  3. モデルの選択を用途に応じて最適化する: 簡単な調査やファイル確認には軽量な高速モデル（Flash系）を使い、複雑なアルゴリズムの設計や難度の高いデバッグにのみ高性能モデル（Pro系）を割り当てます。
  4. 計画（Planning）を活用する: 大きな変更をいきなり行わせるのではなく、まず全体の実装計画を作らせて合意してからコード生成に進むことで、後戻りによる大幅なquota浪費を防ぎます。
ノート練習問題 04-01：weekly quotaを節約するプロンプトの工夫

エージェントに対して「Gymnasiumの環境を作成して」とだけ指示する場合と、どのような仕様や前提条件を付け足して指示する場合とで、エージェントの試行錯誤回数（およびquota消費）がどう変わるか考察してください。

4.3 停止性

アルゴリズム（Algorithm）とは、ある問題を解決するための「有限個の曖昧さのない明確な手順」です。

プログラムがいつまでも終了せずに動き続ける状態を無限ループ（無限実行）と呼びます。正しいアルゴリズムであるための最重要の前提条件の一つが、どのような正当な入力に対しても必ず有限の時間・ステップ数で終了すること（停止性）です。

4.3.1 停止しない例と停止する例

4.3.1.1 1. while True のように絶対に停止しない例

終了条件が全く書かれていない、あるいは脱出条件（break など）が決して成立しない場合、プログラムは永遠に停止しません。 たとえば、「条件式が常に True であり、内部で脱出判定を行わないループ」は、外部から強制終了（Ctrl+C 等）されない限り無限に実行され続けます。

4.3.1.2 2. 変数の値によって停止したりしなかったりする例

ループの終了条件が変数の値に依存している場合、初期値や計算過程によって停止するかどうかが分かれることがあります。 例えば、初期値が正の整数であれば減算によって0に達して終了する処理でも、負の数が入力された場合に減算を続けると永久に0にならず停止しない、といったケースです。また、数学上の難問である「コラッツ予想」（偶数なら2で割り、奇数なら3倍して1を足す操作を繰り返す）のように、任意の入力値に対して必ず1に到達して停止するかどうかを厳密に証明することが極めて難しいアルゴリズムも存在します。

4.3.1.3 3. 停止することを論理的に示せる例

優れたアルゴリズムは、必ず有限回で終了することが数学的・論理的に証明できます。 典型的な証明パターンは、「ループが1回実行されるごとに、ある正の整数値（未処理のデータ件数や目的までの距離など）が必ず1以上減少し、その値が0以下になったときに確実にループが終了する」という構造を持つことです。

ノート練習問題 04-02：停止性の判定

「リストの中から特定の値を探す」手順において、探索範囲の要素を調べるごとに1個ずつ除外していく場合、この処理が必ず有限回で停止する理由を説明してください。

4.4 計算量

同じ目的を果たすアルゴリズムであっても、扱うデータ量（要素数 \(N\)）が増加したときに、必要な計算時間やメモリ領域がどのように増大するかは大きく異なります。このスケーラビリティ（拡張性）を測る指標が計算量（Computational Complexity）です。

4.4.1 時間と空間

計算量には大きく分けて2つの評価軸が存在します：

  • 時間計算量（Time Complexity）: 入力データサイズ \(N\) に対し、アルゴリズム完了までに必要な演算ステップ数（処理時間）の増大度合い。
  • 空間計算量（Space Complexity）: 入力データサイズ \(N\) に対し、実行中に必要となるメモリ領域（記憶容量）の増大度合い。

多くの場合、時間と空間にはトレードオフの関係があります。計算結果をあらかじめメモリ上に表（テーブル）として保持しておけば（空間を消費）、次の計算を一瞬で終えることができます（時間を短縮）。この考え方は、強化学習において状態と行動の価値を記録する「Qテーブル」にも直結しています。

4.4.2 平均と最悪

アルゴリズムの性能は、入力データの並び順や偏りによって変化します：

  • 最悪計算量（Worst-case Complexity）: アルゴリズムにとって最も都合の悪い入力が与えられたときの最大ステップ数。システムの応答時間保証や安全性の評価に不可欠です。
  • 平均計算量（Average-case Complexity）: 起こりうるあらゆる入力パターンに対する計算ステップ数の期待値。実用上の快適さや実測性能を測る指標となります。

例えば、リストから目的の数値を先頭から順に探す場合、目的の値が運悪く一番最後にあるときが「最悪」であり、真ん中あたりで見つかる期待値が「平均」となります。

4.4.3 ビッグオー記法（\(O\) 記法）

データ数 \(N\) が極めて大きくなったときの最悪時（または平均時）の増加率を表す表記法です。

計算量 呼称 特徴・代表例
\(O(1)\) 定数時間 データ数に関係なく一瞬で完了（例: リストのインデックス参照）
\(O(\log N)\) 対数時間 データが倍増してもステップ数は1増える程度（例: 二分探索）
\(O(N)\) 線形時間 データ数に比例してステップ数が増える（例: リストの線形探索）
\(O(N \log N)\) 準線形時間 効率的な整列アルゴリズム（例: クイックソートの平均、マージソート）
\(O(N^2)\) 二乗時間 二重ループ処理（例: 総当たり比較、クイックソートの最悪時）
\(O(2^N)\) 指数時間 組み合わせ爆発。実用的なデータ規模では計算不能になる

4.4.4 線形探索と二分探索の比較（Vibe Codingでの実践）

計算量の圧倒的な違いを体感するために、線形探索（\(O(N)\)）と二分探索（\(O(\log N)\)）を比較するプログラムを coding agent とともに作成します。

ヒントVibe Coding 実践仕様

エージェントに作成を依頼するプログラムの仕様：

  1. 線形探索: 0から順に並んだ100万件の整数リストから、末尾の値（999999）を先頭から順に走査して探索し、比較回数をカウントする。
  2. 二分探索: 同じ100万件のソート済みリストから、中央値との比較を繰り返して探索範囲を半分に絞り込みながら探索し、比較回数をカウントする。
  3. 両方の探索にかかった比較ステップ数を並べて画面に表示する。

エージェントへのプロンプト例： > 「Pythonで100万個の昇順整数リストから末尾の数値を探索するスクリプトを作成してください。線形探索と二分探索の両方を実装し、それぞれの探索にかかった比較ステップ数をカウントして比較表示してください。」

実行すると、線形探索では約100万回の比較が必要であるのに対し、二分探索ではわずか約20回（\(\log_2(1,000,000) \approx 20\)）で完了することが確認できます。

4.5 まとめ

  • coding agentの活用: Antigravity等のツールを使い、仕様の提示・検証・対話改善のサイクルを回す（vibe coding）。
  • weekly quotaの節約: 検索やアイデア出しには通常のchat型AIを活用し、エージェントへの指示は具体的に集約して依頼する。
  • 停止性: 入力に対して有限ステップで必ず終了すること。絶対に停止しない例、変数値による例、論理的証明例を意識して設計する。

1. **検索やアイデア出しには通常のchat型AIを活用する**:
   「Pythonで迷路を作るアイデアを出して」「Gymnasiumのライブラリの概要を教えて」といった一般的な質問や調査は、coding agentではなく無料または枠の大きなchat型AI（GeminiやChatGPTなど）を使って事前に行います。エージェントには「方針が固まった後の実装」のみを依頼します。
2. **指示（プロンプト）を具体的に1回にまとめる**:
   「動かないので直して」のような曖昧で断片的な指示を何度も繰り返すと、quotaを無駄に浪費します。エラーメッセージ全体、実行したコマンド、期待する動作を最初のプロンプトにすべて含めて指示します。
3. **モデルの選択を用途に応じて最適化する**:
   簡単な調査やファイル確認には軽量な高速モデル（Flash系）を使い、複雑なアルゴリズムの設計や難度の高いデバッグにのみ高性能モデル（Pro系）を割り当てます。
4. **計画（Planning）を活用する**:
   大きな変更をいきなり行わせるのではなく、まず全体の実装計画を作らせて合意してからコード生成に進むことで、後戻りによる大幅なquota浪費を防ぎます。

::: {.callout-note icon=false}
### 練習問題 04-01：weekly quotaを節約するプロンプトの工夫
エージェントに対して「Gymnasiumの環境を作成して」とだけ指示する場合と、どのような仕様や前提条件を付け足して指示する場合とで、エージェントの試行錯誤回数（およびquota消費）がどう変わるか考察してください。

## 停止性

**アルゴリズム（Algorithm）**とは、ある問題を解決するための「有限個の曖昧さのない明確な手順」です。

プログラムがいつまでも終了せずに動き続ける状態を**無限ループ（無限実行）**と呼びます。正しいアルゴリズムであるための最重要の前提条件の一つが、どのような正当な入力に対しても**必ず有限の時間・ステップ数で終了すること（停止性）**です。

### 停止しない例と停止する例

#### 1. while True のように絶対に停止しない例
終了条件が全く書かれていない、あるいは脱出条件（`break` など）が決して成立しない場合、プログラムは永遠に停止しません。
たとえば、「条件式が常に `True` であり、内部で脱出判定を行わないループ」は、外部から強制終了（Ctrl+C 等）されない限り無限に実行され続けます。

#### 2. 変数の値によって停止したりしなかったりする例
ループの終了条件が変数の値に依存している場合、初期値や計算過程によって停止するかどうかが分かれることがあります。
例えば、初期値が正の整数であれば減算によって0に達して終了する処理でも、負の数が入力された場合に減算を続けると永久に0にならず停止しない、といったケースです。また、数学上の難問である「コラッツ予想」（偶数なら2で割り、奇数なら3倍して1を足す操作を繰り返す）のように、任意の入力値に対して必ず1に到達して停止するかどうかを厳密に証明することが極めて難しいアルゴリズムも存在します。

#### 3. 停止することを論理的に示せる例
優れたアルゴリズムは、必ず有限回で終了することが数学的・論理的に証明できます。
典型的な証明パターンは、**「ループが1回実行されるごとに、ある正の整数値（未処理のデータ件数や目的までの距離など）が必ず1以上減少し、その値が0以下になったときに確実にループが終了する」**という構造を持つことです。

::: {.callout-note icon=false}
### 練習問題 04-02：停止性の判定
「リストの中から特定の値を探す」手順において、探索範囲の要素を調べるごとに1個ずつ除外していく場合、この処理が必ず有限回で停止する理由を説明してください。
:::

## 計算量

同じ目的を果たすアルゴリズムであっても、扱うデータ量（要素数 $N$）が増加したときに、必要な計算時間やメモリ領域がどのように増大するかは大きく異なります。このスケーラビリティ（拡張性）を測る指標が**計算量（Computational Complexity）**です。

### 時間と空間
計算量には大きく分けて2つの評価軸が存在します：

- **時間計算量（Time Complexity）**: 入力データサイズ $N$ に対し、アルゴリズム完了までに必要な演算ステップ数（処理時間）の増大度合い。
- **空間計算量（Space Complexity）**: 入力データサイズ $N$ に対し、実行中に必要となるメモリ領域（記憶容量）の増大度合い。

多くの場合、時間と空間には**トレードオフの関係**があります。計算結果をあらかじめメモリ上に表（テーブル）として保持しておけば（空間を消費）、次の計算を一瞬で終えることができます（時間を短縮）。この考え方は、強化学習において状態と行動の価値を記録する「Qテーブル」にも直結しています。

### 平均と最悪
アルゴリズムの性能は、入力データの並び順や偏りによって変化します：

- **最悪計算量（Worst-case Complexity）**: アルゴリズムにとって最も都合の悪い入力が与えられたときの最大ステップ数。システムの応答時間保証や安全性の評価に不可欠です。
- **平均計算量（Average-case Complexity）**: 起こりうるあらゆる入力パターンに対する計算ステップ数の期待値。実用上の快適さや実測性能を測る指標となります。

例えば、リストから目的の数値を先頭から順に探す場合、目的の値が運悪く一番最後にあるときが「最悪」であり、真ん中あたりで見つかる期待値が「平均」となります。

### ビッグオー記法（$O$ 記法）
データ数 $N$ が極めて大きくなったときの最悪時（または平均時）の増加率を表す表記法です。

| 計算量 | 呼称 | 特徴・代表例 |
| :--- | :--- | :--- |
| $O(1)$ | 定数時間 | データ数に関係なく一瞬で完了（例: リストのインデックス参照） |
| $O(\log N)$ | 対数時間 | データが倍増してもステップ数は1増える程度（例: 二分探索） |
| $O(N)$ | 線形時間 | データ数に比例してステップ数が増える（例: リストの線形探索） |
| $O(N \log N)$ | 準線形時間 | 効率的な整列アルゴリズム（例: クイックソートの平均、マージソート） |
| $O(N^2)$ | 二乗時間 | 二重ループ処理（例: 総当たり比較、クイックソートの最悪時） |
| $O(2^N)$ | 指数時間 | 組み合わせ爆発。実用的なデータ規模では計算不能になる |

### 線形探索と二分探索の比較（Vibe Codingでの実践）
計算量の圧倒的な違いを体感するために、線形探索（$O(N)$）と二分探索（$O(\log N)$）を比較するプログラムを coding agent とともに作成します。

::: {.callout-tip}
### Vibe Coding 実践仕様
**エージェントに作成を依頼するプログラムの仕様：**

1. **線形探索**: 0から順に並んだ100万件の整数リストから、末尾の値（`999999`）を先頭から順に走査して探索し、比較回数をカウントする。
2. **二分探索**: 同じ100万件のソート済みリストから、中央値との比較を繰り返して探索範囲を半分に絞り込みながら探索し、比較回数をカウントする。
3. 両方の探索にかかった比較ステップ数を並べて画面に表示する。

**エージェントへのプロンプト例：**
> 「Pythonで100万個の昇順整数リストから末尾の数値を探索するスクリプトを作成してください。線形探索と二分探索の両方を実装し、それぞれの探索にかかった比較ステップ数をカウントして比較表示してください。」
:::

実行すると、線形探索では約100万回の比較が必要であるのに対し、二分探索ではわずか約20回（$\log_2(1,000,000) \approx 20$）で完了することが確認できます。

::: {.callout-note icon=false}

## まとめ

- **coding agentの活用**: Antigravity等のツールを使い、仕様の提示・検証・対話改善のサイクルを回す（vibe coding）。
- **weekly quotaの節約**: 検索やアイデア出しには通常のchat型AIを活用し、エージェントへの指示は具体的に集約して依頼する。
- **停止性**: 入力に対して有限ステップで必ず終了すること。絶対に停止しない例、変数値による例、論理的証明例を意識して設計する。
- **計算量**: 時間と空間、平均と最悪の観点からアルゴリズムのスケーラビリティを評価する。強化学習における「状態数の爆発」を理解する上での基礎となる。
